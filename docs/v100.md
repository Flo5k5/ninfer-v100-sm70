# Tesla V100 port

The `sm_70` build is a peer hardware implementation of the same NInfer product surface as the
default `sm_120a` build. It accepts all five registered artifacts and retains Text, Vision, MTP,
prefix reuse, CLI, OpenAI Chat Completions/Responses, Anthropic Messages, and the 35B-A3B text-only
DFlash route. It does not add a second artifact format or model runtime.

## Build

CUDA 12.8 is required: CUDA 13 removed offline compilation for Volta. Configure the architecture
and compiler explicitly:

```bash
cmake -S . -B build-v100 -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_CUDA_COMPILER=/usr/local/cuda-12.8/bin/nvcc \
  -DCMAKE_CUDA_ARCHITECTURES=70
cmake --build build-v100 -j
```

The Volta implementation uses native FP16 tensor cores through CUTLASS where appropriate, exact
Volta kernels for the registered attention/state contracts, and a vendored llama.cpp MMA
flash-attention kernel for long causal prefill. INT8 group-64 KV applies the registered normalized
D256 Hadamard transform to both persistent K and transient Q before the flash calculation.

NVFP4 dense MLP gate/up and down weights are uploaded in checkpoint-native layout and then permuted
in place into the Volta QPN fragment order during model load. The transform covers both the code
and scale planes. Row-scaled FP8 weights receive a corresponding code-plane permutation. Both
transforms preserve allocation sizes, record `VoltaQpnPrepacked` in the runtime weight view, and
release temporary device storage before inference. The artifact on disk is not rewritten. Decode
consumes the QPN layouts directly; wide prefill recognizes them and reconstructs FP16 for its
tensor-core GEMM. FP8 projection groups stage a shared FP16 activation once and reuse it across
their QPN launches.

Learned MTP accepts one through seven draft positions. The native INT8 attention kernel handles
verification widths through seven; the width-eight target round uses the qualified 6+2 attention
composition.

## Qualification

The default Volta run passes all 90 executed CTest cases; six real-artifact cases remain opt-in.
The complete attention contract suite passes for causal BF16/INT8/FP8 paths, packed Vision
attention, and DFlash context attention. The Qwen3.8-27B NVFP4 source-pressure case separately
passes its real-artifact state-materialization path, and the performance sweep loads and exercises
all five artifacts on 32-GiB V100 hardware. NVFP4 and K8V4 KV storage are not available on Volta.

### Context-lookup MTP

MTP has a lossless fast path for output that reproduces the request's own context. The host finds
an earlier occurrence of the current suffix and proposes the tokens that followed it. A round
verifies the copied tokens in a wider target block only when the learned MTP drafts agree with the
copied prefix and every active batch row qualifies. Verification remains the authority for every
emitted token; a miss or disagreement uses the ordinary configured MTP window.

`--lookup-policy` selects when a round widens:

- `fixed` (the default) is the original rule: the nearest earlier occurrence of the exact last
  `--lookup-min-suffix` tokens (default 16), verified with `--lookup-max-proposal` copied tokens
  (default 15). While a copy continues, the round proposes one learned draft as the next agreement
  guard instead of rebuilding the configured window.
- `adaptive` probes copies cheaply and widens fully only once a copy is established. A new copy is
  verified with seven copied tokens (eight query columns, the same attention route as the learned
  window) and regenerates the learned window, so a copy that ends inside the round costs nothing
  in the next one. It moves to the full `--lookup-max-proposal` width once its previous round
  accepted every copied token, or immediately when it matches sixteen tokens of context like the
  fixed rule. After a lookup round the copied source is remembered: when generation returns to it
  just past the point where it diverged (a local edit, the next line of a numbered listing),
  `--lookup-min-suffix` matching tokens resume the copy. Other new copies need a longer suffix,
  tracked per request for tool-call arguments (starting at `--lookup-min-suffix`) and other text
  (starting at 16); a round that gains nothing over the learned drafts doubles its region's
  threshold, a paying round halves it.
- `off` plans no lookup frame.

The original qualification used the V100-PCIe-32GB, CUDA Graphs, INT8 group-64 KV, the optimized
proposal head at the Volta draft-window cap of four, greedy sampling, and a 172-token prompt that
both profiles reproduced verbatim with the fixed rule.

| Qwen3.8-27B profile | Context lookup tok/s | Mean output/round |
|---|---:|---:|
| `groupwise-int` | **130.9** | 12.91 |
| `nvfp4` | **201.0** | 12.91 |

A lookup round is not free. With Qwen3.8-27B NVFP4, INT8 KV, MTP K=4 and the optimized proposal
head at batch one, the submit-to-completion round times are:

| Round | Query columns | Learned drafts proposed | ms, 3-10K context | ms, 26K context |
|---|---:|---:|---:|---:|
| MTP | 5 | 4 | 33.2 | 34.3 |
| lookup, 7 copied | 8 | 1 | 33.1 | |
| adaptive entry, 7 copied | 8 | 4 | about 37 | |
| lookup, 8 copied | 9 | 1 | 38.6 | 40.7 |
| lookup, 15 copied | 16 | 1 | 47.4 | 51.8 |

An eight-column round that proposes one learned draft costs the same as the five-column MTP round
that proposes four; the ninth column alone adds 5.5 ms because attention switches to the chunked
route. Copied text is also what the learned drafts predict best: MTP alone emits 4.8 tokens per
round on it, so a 15-token lookup round must yield about seven tokens to pay, and a round that ends
the copy leaves the next round a single learned draft. The adaptive policy therefore probes copies
at eight columns with a regenerated learned window and widens to sixteen only for established
copies. The entry cost is derived from the adaptive runs' mix of entry and full rounds.

The A/B uses [`tools/bench/run_context_lookup.py`](../tools/bench/README.md#context-lookup-ab):
five fixed workloads of nine requests each, sampled at temperature 1 (top-p 0.95, top-k 20),
thinking off, the production serve profile (`--kv-dtype int8 --spec mtp --draft-tokens 4
--lm-head-draft --max-context 220000 --vision`). `rewrite` returns a 2-4K-token source file after
two small edits, `edits` and `write` are coding-agent turns after a `cat -n` Read result (Edit
calls copying lines, one Write call holding the whole edited file), `prose` asks short questions,
and `summary` summarizes a 25K-token document. Each cell pools the decoded tokens over the decode
time of its nine requests.

| Policy | rewrite | edits | write | prose | summary |
|---|---:|---:|---:|---:|---:|
| `off` | 142.4 | 126.6 | 141.1 | 83.2 | 91.8 |
| `fixed`, suffix 16 (default) | 302.4 | 131.5 | 141.5 | 80.3 | 87.9 |
| `fixed`, suffix 8 | 288.1 | 126.5 | 138.5 | 85.2 | 91.3 |
| `fixed`, suffix 4 | 254.0 | 143.8 | 135.9 | 84.2 | 92.2 |
| `fixed`, suffix 16, 8 copied | 216.8 | 136.5 | 142.2 | 82.3 | 93.8 |
| `fixed`, suffix 16, 7 copied | 224.9 | 124.5 | 141.2 | | |
| `adaptive`, suffix 4 | 309.3 | 137.6 | 146.2 | 82.9 | 84.5 |

Decode tok/s. Shorter fixed suffixes widen on incidental matches and pick wrong sources in copied
code; narrower fixed proposals lose most of the long-copy gain. Prose and summary widen on at most
4% of rounds under every policy, so their differences are sampling variance (the per-step cost is
unchanged): with temperature 1, the learned-draft acceptance of the sampled continuations varies
more between runs than lookup changes it. The paired runs below remove the host-load variance
between sessions by running both policies in overlapping runs, one per GPU, and again with the GPUs
swapped:

| Workload | `fixed`, suffix 16 | `adaptive`, suffix 4 | Gain |
|---|---:|---:|---:|
| rewrite | 299.0 (46.0 ms x 13.76) | 310.6 (46.3 ms x 14.39) | +3.9% |
| edits | 131.4 (35.5 ms x 4.67) | 145.6 (37.1 ms x 5.41) | +10.7% |
| write | 142.6 (34.1 ms x 4.87) | 146.9 (34.8 ms x 5.11) | +3.0% |
| prose | 82.4 (33.1 ms x 2.73) | 83.1 (33.2 ms x 2.75) | +0.8% |
| summary | 91.6 (36.2 ms x 3.32) | 94.6 (35.9 ms x 3.40) | +3.3% |

Decode tok/s (ms per step x tokens per step), 18 requests per cell pooled over both GPU
assignments; the two runs agree within their bootstrap intervals. The adaptive policy widens 90% of
rewrite rounds (14.6 of 15 copied tokens accepted), 30% of edits rounds and 16% of write rounds,
two thirds of the latter through the entry tier. Prose never widened, and summary widened on 1-2%
of rounds under both policies, so their differences are sampling variance at an unchanged step
cost.

Greedy outputs are not bit-identical across policies. Every emitted token is still the target's
own choice, but the V100 verification numerics depend on the block width, so a copied round can
round a near-tie differently from the MTP round that would otherwise have verified that position.
Over twelve greedy requests (two rewrite, three edits, two write, three prose, two summary), the
fixed rule differed from MTP-only decoding on three, from the first differing token onward (one
edit turn and the two identical summary requests); the adaptive policy differed on the same two
summary requests, and from the fixed rule on the edit turn, where it reproduced the MTP-only output.
Repeated runs of one policy reproduced their greedy outputs exactly. The width dependence is not
specific to lookup: plain MTP with seven learned drafts (eight columns) differed from four drafts
on two of eight greedy requests, one of them at the same position as the lookup policies.

## Preferred SXM2 device

On a dual-V100 host, set `NINFER_GPU_UUID` to the UUID of the intended SXM2 and invoke
`tools/v100/ninfer-sxm2.sh`. The launcher validates that the selected device is a
`Tesla V100-SXM2-32GB`, sets `CUDA_VISIBLE_DEVICES`, and runs `build-v100/apps/ninfer`:

```bash
NINFER_GPU_UUID=<sxm2-uuid> tools/v100/ninfer-sxm2.sh --help
```

Set `NINFER_EXECUTABLE` when the binary lives elsewhere. UUID selection prevents PCI enumeration
from silently moving benchmarks to a PCIe-board GPU. The executable still receives `--device 0`,
because CUDA remaps the selected UUID to logical device zero.

For Qwen3.8-27B serving, pass `--prefill-chunk 2048`. On the preferred SXM2 with the NVFP4 artifact
and INT8 KV, an 8,192-token prefill measured 1,137.0 tok/s versus 1,078.6 tok/s with the generic
1,024-token default, a 5.4% improvement.
