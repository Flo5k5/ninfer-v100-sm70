# Tesla V100 port

The `sm_70` build is a peer hardware implementation of the same NInfer product surface as the
default `sm_120a` build. It registers the same five artifacts and retains Text, Vision, MTP,
prefix reuse, CLI, OpenAI Chat Completions/Responses, Anthropic Messages, and the 35B-A3B text-only
DFlash route. It does not add a second artifact format or model runtime. The README's
[Models](../README.md#models) section says which version-3 artifacts load on this port today.

## Build

CUDA 12.8 is required: CUDA 13 removed offline compilation for Volta. Configure the architecture
and compiler explicitly:

```bash
cmake -S . -B build-v100 -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_CUDA_COMPILER=/usr/local/cuda-12.8/bin/nvcc \
  -DCMAKE_CUDA_ARCHITECTURES=70
cmake --build build-v100 -j
```

The Volta implementation uses native FP16 tensor cores through CUTLASS where appropriate, exact
Volta kernels for the registered attention/state contracts, and a vendored Split-D flash-attention
kernel with FP32 accumulators for long causal prefill (see [Long-context numerics](#long-context-numerics)).
INT8 group-64 KV applies the registered normalized D256 Hadamard transform to both persistent K and
transient Q before the flash calculation.

NVFP4 dense MLP gate/up and down weights are uploaded in checkpoint-native layout and then permuted
in place into the Volta QPN fragment order during model load. The transform covers both the code
and scale planes. Row-scaled FP8 weights receive a corresponding code-plane permutation. Both
transforms preserve allocation sizes, record `VoltaQpnPrepacked` in the runtime weight view, and
release temporary device storage before inference. The artifact on disk is not rewritten. Decode
consumes the QPN layouts directly; wide prefill recognizes them and reconstructs FP16 for its
tensor-core GEMM. FP8 projection groups stage a shared FP16 activation once and reuse it across
their QPN launches.

Learned MTP accepts one through seven draft positions. The native INT8 attention kernel handles
verification widths through seven; the width-eight target round uses the qualified 6+2 attention
composition.

## Qualification

Before the v3 artifact port, the default Volta run passed all 90 executed CTest cases, with six
real-artifact cases opt-in.
The complete attention contract suite passes for causal BF16/INT8/FP8 paths, packed Vision
attention, and DFlash context attention. The Qwen3.8-27B NVFP4 source-pressure case separately
passes its real-artifact state-materialization path, and the performance sweep loaded and exercised
all five artifacts, in their version-2 form, on 32-GiB V100 hardware. NVFP4 and K8V4 KV storage are
not available on Volta.

## Long-context numerics

On long, near-deterministic text (source code, tool-call arguments), NInfer drifted much further
from an exact evaluation of its own quantized weights than llama.cpp does on the same weights (mean
KLD 0.33 against 0.004 on tool calls, below). Two Volta mechanisms grow with depth and context: the
text residual stream is stored in BF16 (an 8-bit significand, rounded twice per layer, 128 times
per token on the 64-layer 27B), and the vendored llama.cpp flash kernel of the prefill route keeps
its P.V accumulators in FP16. Two startup options of `ninfer`, `ninfer-serve`,
`ninfer-perplexity` and `ninfer_bench` (Engine options `prefill_attention` and `text_residual`)
address them:

- `--prefill-attention auto|splitd|flash|reference` selects the wide causal prefill kernel for
  BF16 and INT8 KV. `splitd` is the vendored Split-D D256 kernel (`third_party/sm70_flash_d256`,
  from 1Cat-vLLM through sm70-attn), with FP16 operands and FP32 accumulators for Q.K^T and P.V;
  `flash` is the llama.cpp MMA kernel, whose FP16 P.V accumulation exceeds the attention
  criterion on near-uniform attention over 16k keys; `reference` is the direct FP32 kernel, for
  numerical A/B only. `auto` (the default) selects `splitd` on the 27B attention geometry, where it
  was measured below, and keeps `flash` on 35B-A3B.
- `--text-residual fp32` (`bf16` is the default) keeps the residual stream in FP32 through
  prefill, decode and verification: the FP8 token embedding, the input norms, every FP8/NVFP4
  residual projection (fused into the narrow-width epilogues, accumulated from the row-scaled FP32
  GEMM accumulators at prefill widths) and the vision embedding scatter read or write FP32. It is
  available for the Qwen3.8-27B NVFP4 artifact; Engine startup rejects it for other artifacts and
  with DFlash, which reads its target features from the BF16 stream.

The table reports the mean KLD against an FP32 evaluation of the NVFP4 weights (the artifact's
weights decoded into an F16 GGUF and run layer by layer in PyTorch FP32), on the three 32,768-token
windows of the long KLD corpus (16,383 scored positions each), with INT8 KV. llama.cpp's CUDA path
on the same GGUF, with an FP32 residual and FP16 GEMM operands, shows what that precision reaches.
The decode rows score the targets 4 columns at a time (`ninfer-perplexity --scored-chunk 4`),
through the narrow-width kernels that generation uses.

| NInfer, BF16 residual, `flash` | 0.00049 | 0.0369 | 0.331 |

A few positions carry the code window's mean (NInfer's 95% block-bootstrap intervals run from about
0.4 to 1.7 times each value), so its BF16 rows do not rank the two kernels; the tool-call intervals
stay within 15% of each value.

Emulating NInfer's storage roundings in the FP32 evaluation attributes the rest: BF16 at every
activation site gives 0.033 (code) and 0.275 (tool calls), the BF16 residual alone 0.026 and 0.247,
every site but the residual 0.096 (tool calls), and FP16 at every site 0.0021 and 0.021. With an
FP32 residual the remaining error comes from the other BF16 activations (norm outputs about a
quarter of it, then projection, attention, Gated DeltaNet and FFN outputs) and from INT8 KV (BF16 KV
brings the tool-call KLD from 0.110 to 0.090, near that 0.096); BF16 logits alone cost 0.0001.

Against the BF16 model the tool-call window is dominated by the weight quantization itself (mean
KLD 0.947 for llama.cpp F16, 0.948 and 0.949 for NInfer with split-D and the BF16 or FP32 residual),
so there the FP32 residual shows on code (0.099 to 0.085, llama.cpp 0.086). The tool-call perplexity
does not rank the configurations: the FP32 evaluation itself is 12.3% above the BF16 model,
llama.cpp 11.6%, NInfer 13.4% with the BF16 and 15.1% with the FP32 residual, the reverse of their
KLD order.

|---|---:|---:|---:|---:|

the previous production path against the BF16 model (mean KLD 0.0212 against 0.0219; llama.cpp F16

### Context-lookup MTP

MTP has a verified fast path for output that reproduces the request's own context. The host finds
an earlier occurrence of the current suffix and proposes the tokens that followed it. A round
verifies the copied tokens in a wider target block only when the learned MTP drafts agree with the
copied prefix and every active batch row qualifies. Verification remains the authority for every
emitted token; a miss or disagreement uses the ordinary configured MTP window.

`--lookup-policy` selects when a round widens; every lookup flag requires `--spec mtp`:

- `fixed` (the default) is the original rule: the nearest earlier occurrence of the exact last
  `--lookup-min-suffix` tokens (default 16), verified with `--lookup-max-proposal` copied tokens
  (default 15). While a copy continues, the round proposes one learned draft as the next agreement
  guard instead of rebuilding the configured window.
- `adaptive` probes copies cheaply and widens fully only once a copy is established. When
  `--draft-tokens` is below seven and `--lookup-max-proposal` above it, a new copy enters through a
  seven-token tier (eight query columns, the same attention route as the learned window) that also
  regenerates the learned window, so a copy that ends inside the round costs nothing in the next
  one; otherwise a new copy is verified at the full width. A copy moves to the full
  `--lookup-max-proposal` width once its previous round accepted every copied token, or at once
  when it matches sixteen tokens of context like the fixed rule. After a lookup round the copied
  source is remembered: when generation returns to it just past the point where it diverged (a
  local edit, the next line of a numbered listing), `--lookup-min-suffix` matching tokens resume
  the copy. Other new copies need a recurring suffix at least as long as a per-request threshold,
  one for tool-call arguments and one for other text, and `--lookup-min-suffix` is the floor of
  both: tool-call arguments start at it and other text starts at 16 (or at the floor, if higher).
  A round that pays (it accepts its whole proposal, or at least four tokens more than the agreeing
  learned drafts) halves its region's threshold toward the floor; a round that adds fewer than two
  tokens beyond them doubles it toward 64. The floor therefore also reaches ordinary text: with
  `--lookup-min-suffix 4`, prose widens on four-token matches after two paying rounds.
- `off` plans no lookup frame. `--lookup-min-suffix` and `--lookup-max-proposal` have no effect
  then, and the executables reject them.

Each planned lookup width is its own verification frame with ReplaySSM records and a CUDA Graph
family for every lane. With `fixed` the MTP backend holds two graph families; the adaptive entry
tier adds a third, 50% more MTP graph memory per lane. With Qwen3.8-27B NVFP4 at 220K context and
one lane, the CUDA Graph allowance is 82 MiB with `off`, 164 MiB with `fixed` and 246 MiB with
`adaptive`, and the whole runtime reservation grows by 118 MiB from `off` to `fixed` and by 100 MiB
more for `adaptive`.

The original qualification used the V100-PCIe-32GB, CUDA Graphs, INT8 group-64 KV, the optimized
proposal head with four learned drafts, greedy sampling, and a 172-token prompt that both profiles
reproduced verbatim with the fixed rule.

| Qwen3.8-27B profile | Context lookup tok/s | Mean output/round |
|---|---:|---:|
| `groupwise-int` | **130.9** | 12.91 |
| `nvfp4` | **201.0** | 12.91 |

A lookup round is not free. With Qwen3.8-27B NVFP4, INT8 KV, MTP K=4 and the optimized proposal
head at batch one, the submit-to-completion round times are:

| Round | Query columns | Learned drafts proposed | ms, 3-10K context | ms, 26K context |
|---|---:|---:|---:|---:|
| MTP | 5 | 4 | 33.2 | 34.3 |
| lookup, 7 copied | 8 | 1 | 33.1 | |
| adaptive entry, 7 copied | 8 | 4 | about 37 | |
| lookup, 8 copied | 9 | 1 | 38.6 | 40.7 |
| lookup, 15 copied | 16 | 1 | 47.4 | 51.8 |

An eight-column round that proposes one learned draft costs the same as the five-column MTP round
that proposes four; the ninth column alone adds 5.5 ms because attention switches to the chunked
route. Copied text is also what the learned drafts predict best: MTP alone emits 4.8 tokens per
round on it, so a 15-token lookup round must yield about seven tokens to pay, and a round that ends
the copy leaves the next round a single learned draft. The adaptive policy therefore probes copies
at eight columns with a regenerated learned window and widens to sixteen only for established
copies. The entry cost is derived from the adaptive runs' mix of entry and full rounds.

The A/B uses [`tools/bench/run_context_lookup.py`](../tools/bench/README.md#context-lookup-ab):
five fixed workloads of nine requests each, sampled at temperature 1 (top-p 0.95, top-k 20),
thinking off, the production serve profile (`--kv-dtype int8 --spec mtp --draft-tokens 4
--lm-head-draft --max-context 220000 --vision`). `rewrite` returns a 2-4K-token source file after
two small edits, `edits` and `write` are coding-agent turns after a `cat -n` Read result (Edit
calls copying lines, one Write call holding the whole edited file), `prose` asks short questions
in French and English, and `summary` summarizes a 25K-token French document. Decode tok/s pools
the tokens decoded after the first one, which prefill produces, over the decode time of the
requests in a cell; per-step figures divide by the decode rounds of the server's request log.

Decode tok/s. Paired request by request with the default, the copy-heavy differences are clear
(95% intervals): on rewrite, shorter suffixes widen on incidental matches and pick wrong sources
in copied code, losing 4.7% (-6.3% to -3.2%) at 8 tokens and 16.0% (-18.9% to -12.6%) at 4, while
eight or seven copied tokens lose 28% and 26%, most of the long-copy gain; a 4-token suffix gains
9.3% (+4.2% to +14.2%) on edits. Prose and summary widen on at most 4% of rounds under every
policy and change the step cost by at most 2%, so their differences are sampling variance: at
temperature 1, the acceptance of the sampled continuations varies more between runs than lookup
changes it. One of them, suffix 8 over 16 on prose (+6.0%), even has an interval that excludes

of this series is only clearly ahead on write (+3.3%, +2.0% to +4.5%).

Decode tok/s (ms per step x tokens per step), then the changes with their intervals. The gains on
rewrite, edits and write are significant: their intervals exclude zero. Adaptive steps are slower,
since entry rounds cost more than learned rounds, and the extra tokens per step more than make up
for it. The edits gain is the least precise: the two GPU assignments measured +18.4% and +2.4% on
their own, from nine short requests each. The prose and summary differences are not significant:
prose never widened and summary widened on 1% of rounds under both policies, the step cost is
unchanged, and what remains is sampling variance in the tokens per step. The adaptive policy widens
91% of rewrite rounds (14.6 copied tokens accepted per lookup round), 31% of edits rounds and 17% of
write rounds, about two thirds and three quarters of the latter two through the entry tier.

Greedy outputs are not bit-identical across policies. Every emitted token is still the target's
own choice, but the V100 verification numerics depend on the block width, so a copied round can
round a near-tie differently from the MTP round that would otherwise have verified that position.
Over twelve greedy requests (two rewrite, three edits, two write, three prose, two summary), the
fixed rule differed from MTP-only decoding on three, from the first differing token onward (one
edit turn and the two identical summary requests); the adaptive policy differed on the same two
summary requests, and from the fixed rule on the edit turn, where it reproduced the MTP-only output.
Repeated runs of one policy reproduced their greedy outputs exactly. The width dependence is not
specific to lookup: plain MTP with seven learned drafts (eight columns) differed from four drafts
on two of eight greedy requests, one of them at the same token where the first series' 4-token
suffix and 7-copied-token variants of the fixed rule also diverged.

## Preferred SXM2 device

On a dual-V100 host, set `NINFER_GPU_UUID` to the UUID of the intended SXM2 and invoke
`tools/v100/ninfer-sxm2.sh`. The launcher validates that the selected device is a
`Tesla V100-SXM2-32GB`, sets `CUDA_VISIBLE_DEVICES`, and runs `build-v100/apps/ninfer`:

```bash
NINFER_GPU_UUID=<sxm2-uuid> tools/v100/ninfer-sxm2.sh --help
```

Set `NINFER_EXECUTABLE` when the binary lives elsewhere. UUID selection prevents PCI enumeration
from silently moving benchmarks to a PCIe-board GPU. The executable still receives `--device 0`,
because CUDA remaps the selected UUID to logical device zero.

For Qwen3.8-27B serving, pass `--prefill-chunk 2048`. On the preferred SXM2 with the NVFP4 artifact
and INT8 KV, an 8,192-token prefill measured 1,137.0 tok/s versus 1,078.6 tok/s with the generic
1,024-token default, a 5.4% improvement.
